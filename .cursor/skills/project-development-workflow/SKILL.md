# 项目开发流程

## 核心原则

- 先理解项目现状，再修改代码；优先复用已有抽象、工具和生命周期，不重复创建功能。
- 以最小范围完成需求，避免无关重构、格式化、重命名和依赖升级。
- 尊重项目已有规则、目录结构、命名、类型系统和用户未提交的修改。
- 所有实现、说明和注释使用简体中文；涉及公共 API 时同时考虑类型、文档和示例。

## 工作流程

### 1. 分析

1. 明确用户要解决的问题、预期行为和影响范围。
2. 检查 Git 状态，识别已有修改，避免覆盖或混入无关变更。
3. 阅读相关入口、类型定义、调用方、插件或工具实现，以及对应文档。
4. 在修改前确认现有实现是否已经提供相同能力。
5. 对复杂任务先给出简短方案；对简单任务直接实施。

### 2. 实现

1. 选择与现有架构一致的实现位置，不绕过已有公共入口或状态管理流程。
2. 优先保持公开 API 兼容；必要的破坏性变更必须明确说明影响。
3. 正确处理空值、错误、异步竞态、取消、组件卸载和资源清理。
4. 修改配置或公共行为时，同步更新类型、实现、导出、文档和示例。
5. 不修改构建产物、依赖缓存或与当前任务无关的文件。

### 3. 验证

1. 先检查修改后的文件和差异，确认没有意外改动。
2. 运行项目已有的最相关检查、类型检查、测试或构建脚本。
3. 发现失败时区分原有问题和本次引入的问题，并优先修复本次问题。
4. 复查边界条件，尤其是响应式值、生命周期、异步错误和重复执行。

## 输出要求

- 完成后说明修改了什么、解决了什么问题、验证执行了什么以及是否存在未解决问题。
- 引用代码时提供文件路径和准确行号；不要用未经验证的行号或推测性结论。
- 用户只询问分析时保持只读，不主动修改代码；用户明确要求修改时才执行写入操作。
- 生成提交信息时使用中文，并遵循项目现有的提交格式；例如 `feat: 修复请求取消后的状态更新`。
